Canonical messages and wire conversions.

Content parts

The content of a message can be a list of parts. Each part is a dict with a type. mk_content(o) builds one part. The result depends on the input:

input result
a string a text part
bytes or a path, holding an image an image_url part with the picture embedded as a base64 data URL
bytes or a path, holding audio an input_audio part
a dict the dict, unchanged. Urai assumes it is a part already.
any other bytes or path, such as a PDF TypeError
any other type TypeError

mk_content reads the bytes of a path and inspects them to find the type. The TypeError reports an attachment that the model cannot read. Urai never drops it silently.

is_media(p) returns True when a part is an image part or an audio part.

Messages

mk_msg(content, role) builds one message from a string, bytes, a path, or a list that mixes these. A message dict is returned unchanged. None is also returned unchanged. When every part is text, mk_msg joins the parts with newlines into one string. A message with a part that is not text keeps the list form. An image part is an example. mk_msgs applies mk_msg to a list of messages.

A picture in the history is sent again with every later turn. It costs the same tokens each time. strip_media(m) replaces each media part in a message with the placeholder [image] or [audio]. It joins the content with newlines into one string. The history still records that a picture was there. Call strip_media on past turns before you send them. strip_hist_media(hist) does the same for a whole history. Use it to save a conversation to disk without the base64 data.

Tools

A tool schema is a JSON description of a tool. It gives the name, a description, and the parameters. mk_toolspec(f) builds the schema from a Python function with fastcore.funccall.get_schema. get_schema reads the name of the function, its docstring, its type annotations, and the comment after each parameter.

mk_toolspec returns a dict unchanged. Urai assumes the dict is a schema already. Use a dict to describe a tool that the provider runs itself, such as a hosted web search.

mk_toolspec handles two cases without the plain get_schema result. For a pydantic model, it uses model_json_schema. It inlines each $ref and removes the title keys. get_schema reads a pydantic model as one opaque data field.

For a Literal annotation, mk_toolspec writes an enum with the JSON type of the values. This holds for a Literal alone and for a Literal inside Optional, a union or a list. get_schema writes "object[object, object]" for these, which is not a JSON Schema type. Strict providers such as Gemini refuse such a schema.

Tool calls

When the model asks for a tool, the reply holds a list of tool calls. ToolCall(name, arguments) builds one in the canonical form. It is a dict, so code that indexes it as tc['function']['name'] keeps working, and it adds name, arguments and server properties for easier reading. server=True marks a call the provider has already run on its side, such as a hosted web search; the tool loop records such calls but never runs them locally.

The other helpers work on plain dicts as well as ToolCall. tc_name(tc) reads a call’s name, tool_rows(m) lists the (name, arguments) of every call in a message, and mk_tool_res_msg(tc, result) builds the role='tool' message that sends a result back to the model, linked to the call by its id. mk_tool_res_msgs does that for several calls at once.

Most providers accept only text in a tool result message, so a tool cannot hand back a screenshot directly. A tool that produces pictures returns ToolMedia(text, media), a string that also carries a list of image paths or bytes. The text goes into the tool message as usual. After all the results of a step, the tool loop sends the pictures to the model in one extra user message. tool_media(o) returns the pictures a result carries, or an empty list.

test_eq(type(mk_tool_res_msg(ToolCall('s'), r)['content']), str)
test_eq([tool_media('x'), tool_media(3), tool_media(ToolMedia('x'))], [[], [], []])

Small models often get argument types wrong. They write "3" where the schema asks for an integer, "true" for a boolean, or a JSON string where an object or a list belongs. Sometimes they nest all the arguments one level down, under a key such as arguments.

coerce_args(args, params) converts each argument to the type its schema declares: numbers, booleans (true, yes, on and their opposites), strings, arrays (a single value becomes a one-item list) and objects. The type always comes from the schema, never from how the value looks, and a value that cannot be converted safely is left as the model wrote it. Arguments without a declared type, or with a union type, are not touched. hoist_buried(args, params) lifts missing required parameters out of a nested container, but only when one container holds all of them. coerce_tcs(tcs, toolspecs) applies both to every call in a list, using each tool’s own schema found by toolspec_params, and leaves calls to tools with no schema alone. The tool loop runs it on each step.

         'required': ['ok']}

test_eq(tcs[1]['function']['arguments'], {'a': '3'})   # no spec names it, so nothing is assumed

In from the wire

norm_resp(r) converts a completion in the OpenAI response format into a Resp, the urai reply object. It does these steps:

  • It moves <think> text into channels['thought'].
  • It puts the native tool calls of the provider and the tagged calls in the text into one tool_calls list.
  • It sets truncated when the model stopped at the token limit.
  • It keeps usage.

If the text has a tool block that norm_resp cannot parse, it sets tool_parse_failed on the reply. The tool loop then asks the model to send the call again.

A provider sends native tool arguments as a JSON string. parse_args decodes the string. It returns a dict unchanged. It returns None for empty strings, invalid JSON, or JSON values that are not objects. It does not raise for these inputs. norm_resp marks these calls unread and sets tool_parse_failed. The loop can ask for the call again. A valid {} remains readable.

stream_resp(split, ...) builds a Resp at the end of a streamed step. Its inputs are a finished StreamSplit and the tool calls, thinking text and usage that the backend collected.

Out to the wire

History messages carry keys that providers reject, such as channels and usage. to_oai_msg(m) converts a history message into a message that an OpenAI-compatible API accepts.

Input Result
A key other than role, content, tool_calls, tool_call_id or name Dropped
A key with the value None Dropped
Tool call arguments that are a dict Encoded as a JSON string
A tool call with no id id set to call_ plus the position of the call, such as call_0
A message with tool_calls and no content content set to ''

Several providers refuse a message with tool calls and no content.

Usage across rounds

A turn with tool calls takes several requests to the model. The first request gets the calls. The next request follows the tool results. sum_usage(us) adds the usage dicts of these requests and skips None. It returns None when no request reported usage. The first model name found in the dicts is kept.

Key in the result When it appears
prompt_tokens, completion_tokens, total_tokens, cached_tokens Always
reasoning_tokens, cache_creation_tokens, cost Only when the sum is not zero
model Only when a usage dict names one

The optional totals reasoning_tokens, cache_creation_tokens and cost are left out when their sum is zero. A local model that reports no cost leaves cost out of the result.

source

Prompt transports

Some backends take one block of text instead of a list of messages. These backends have no tokenizer of their own. A tokenizer splits text into tokens, the units that a model counts.

est_tokens(text) estimates the token count of text. It divides the length by CHARS_PER_TOKEN, which is 3.25, and rounds up. It returns 0 for empty text.

render_prompt(hist, sp) writes a conversation as one block of text. The block starts with the system prompt sp. Each message then gets a heading and its text. A message with no text and no tool calls is skipped. The table shows the headings.

Message role Heading
user ## User
assistant ## Assistant
system ## System
tool ## Tool result (name), with the tool name in the brackets

A tool call is written as a tool_call block with a JSON object that has name and arguments. This is the form that tag_tools_sp teaches the model. The example renders a short conversation with one tool call.

Prefix reuse

A local engine keeps a KV cache. The KV cache holds the model state for the tokens that the engine has already processed. When a new prompt starts with the same tokens as the last prompt, the engine reuses that part of the cache and processes only the new tokens. common_prefix_len(a, b) returns the number of leading items that two token lists share. This number is the count of tokens that a backend can reuse.
