Reading thinking and tool calls out of plain text.

Thinking

split_think(text) returns (clean_text, thought). clean_text is the reply with its leading <think> blocks removed. thought is the text of those blocks. Several leading blocks are joined with newlines. Only a block at the start of the reply is thinking. A think tag that appears after the answer has started, for example when the answer explains the tag, is answer text and stays in clean_text. The function also handles two damaged forms. If a leading <think> never closes, everything after it counts as thinking. This happens when the reply ran out of tokens in mid-thought. If a </think> has no opener before it, everything before it counts as thinking. This happens when the chat template already wrote the opening tag into the prompt.

A call in the text

The body of a <tool_call> block should be a JSON object with a name and an arguments object. The helpers below turn whatever the model wrote into a tool call dict. The dict has the OpenAI form {'id', 'type': 'function', 'function': {'name', 'arguments'}}. mk_tc builds it.

Small models often write JSON that a strict parser rejects. loose_json(s) tries strict json.loads first. Valid input is never altered. If strict parsing fails, loose_json uses a tolerant reader. The tolerant reader accepts these mistakes:

  • quotes inside a string that were never escaped
  • raw newlines inside strings
  • single-quoted strings and unquoted keys
  • Python True, False and None
  • trailing commas

loose_json returns (obj, complete). complete is False when the text stopped before the object closed. A value that was cut off is left out of obj. A half-written argument is never returned as if it were whole. Input that does not start with { gives (None, False).

Qwen 3.5 and later chat templates ask the model for calls in an XML form: <function=read><parameter=path>a.txt</parameter></function>. Claude uses a similar form of its own: <invoke name="read"><parameter name="path">...</parameter></invoke>. parse_fn_tags reads both.

parse_fn_tags decodes a parameter value that spells a JSON number, boolean, null, object or array. Other values stay strings. The one newline that the template puts on each side of a value is removed. Only parameters with a closing </parameter> are kept. A cut-off call returns its name and the parameters that finished.

parse_tool_tags tries this XML form before JSON. It reads a <tool_call> block that contains <function= as XML. Text inside a parameter value is never mistaken for the tool name.

def parse_fn_tags(

Tool calls written in the <function=name> or <invoke name=...> XML form.

tcs = parse_fn_tags('<tool_call>\n<function=read>\n<parameter=path>\na.txt\n</parameter>\n</function>\n</tool_call>')

Some models drop the tags and answer with only the call object. The object is sometimes inside a ```json fence. lone_tag_tc accepts it only when all of these hold. The object is the entire reply. The object has a name and an arguments field. When you pass names, the name is one of your tools. A reply that describes or quotes JSON fails one of these checks and does not become a call.

Arguments that cannot be read keep the call marked unread. They never become a readable empty argument object.

parse_tool_tags(text, names) is the function that a backend calls on a finished reply. It returns the reply text with the tool blocks removed, and the list of calls. It reads <tool_call> blocks in JSON or XML form. It reads bare <function=...> and <invoke ...> blocks. It reads a final <tool_call> that the model opened and never closed. The bare-object fallback above runs only when no tagged call was found and no block failed.

A model sometimes keeps writing after its last call. That text comes before the result exists, so it is often a result the model made up. parse_tool_tags drops all text after the last call. Text before a call and between calls stays.

A model sometimes writes its own result markup, such as <tool_result>42</tool_result>. parse_tool_tags strips those tags. Their contents stay as ordinary text and never become a call.

A damaged reply in the <invoke> form can leave <parameter> elements between its calls. When the reply holds an <invoke> or <function=...> call, parse_tool_tags strips these stray parameters with their contents. A reply with no such call keeps any <parameter> text that it quotes.

parse_tool_tags_ex does the same and returns a third value, failed. failed is True when the reply held a tool block that nothing could read. Use it to tell the model that its call was lost.

Putting schemas in the prompt

tag_tools_sp(toolspecs, sp) appends a tool section to the system prompt sp. The section lists the JSON schema of each tool inside <tools></tools>. It shows the <tool_call> format. It tells the model to send independent calls together, to stop after its last call, and to never make up a result. Results come back in the next message under a ## Tool result (name) heading. With no tools, the function returns sp unchanged. Pass template to use different wording. The template must contain a {tools} placeholder. Write any other literal brace as {{ or }}.

source

tag_tools_sp

def tag_tools_sp(
    toolspecs, sp:str='',
    template:str='\n\n# Tools\n\nYou can call the functions below. Their signatures are given as JSON schemas inside <tools></tools>:\n\n<tools>\n{tools}\n</tools>\n\nTo call one, emit a JSON object with the function\'s name and its arguments inside <tool_call></tool_call>:\n\n<tool_call>\n{{"name": "the_function_name", "arguments": {{"first": "value"}}}}\n</tool_call>\n\nCalls that do not depend on each other\'s results -- reading several files, running several searches -- go together in one message, each in its own <tool_call> block, one after another. A call that needs an earlier result waits for it.\n\nAfter the last </tool_call>, end your reply and wait. Nothing may follow it in the same message: not a comment, and not a guess at what a result will be.\n\nDo not describe a call in prose as well as emitting it, and never invent a result -- the real ones come back in the next message, each under a "## Tool result (name)" heading. That heading is the only form a result ever takes: do not write result markup of your own, do not wrap a result in tags, and do not copy a result back into your reply. Say what you concluded from it, not what it said.'
):

Append the tool schemas and the <tool_call> instructions to the system prompt sp.

Streaming

A tag can be split across two deltas of a streamed reply. A delta is one piece of streamed text. For example, one delta ends in <thi and the next starts with nk>. StreamSplit holds back the end of its buffer when that end could be the start of a tag. It decides when more text arrives.

Call feed(delta) with each piece of text and call finish() at the end. Both yield chunk dicts. Thinking comes out as {'channels': {'thought': ...}} chunks. Answer text comes out as {'content': [...]} chunks. The raw JSON or XML of a tool call is never passed through as text. StreamSplit buffers it until the block closes. It then parses the block with parse_fn_tags and mk_tag_tc, which parse_tool_tags also uses, and collects the result in tool_calls. The stream path does not apply the lone_tag_tc fallback. After the stream ends, text, thought and tool_calls hold the whole reply. failed is True if a tool block could not be read.

The hand-written cases on this page cannot cover everything that real models write. To collect real examples, set the environment variable URAI_RAW_DUMP to a file path. A StreamSplit then keeps the raw text it was fed. The tool loop appends each such reply from a chat with tools to that file. Each reply is one JSON line that holds the tool schemas and the raw reply. tests/test_tool_traffic.py replays captured replies through the parser. tests/harvest_tool_traffic.py merges a capture file into the replay corpus. RAW_DUMP() returns the path and reads the variable on each call. dump_raw appends one record. When the variable is unset, each reply costs one environment lookup.

StreamSplit

def StreamSplit(
    keep_raw:NoneType=None
):

Split a streamed reply into thinking chunks, text chunks and parsed tool calls.

def _run(deltas):
    "Feed `deltas` through a fresh splitter and return it with the chunks it produced."
    s = StreamSplit()
    chunks = [c for d in deltas for c in s.feed(d)] + list(s.finish())
    return s, chunks

ordered, _ = _run([b2[i:i+3] for i in range(0, len(b2), 3)])

ordered.tool_calls

Hosted APIs that support tools natively also stream them in pieces. OpenAI sends each tool call as a series of fragments. Each fragment has the index of its call. The first fragment holds the id and the name. Later fragments hold more of the arguments string. acc_tc(acc, deltas) adds the fragments of one delta to acc. After the last delta, acc holds one complete call for each index. The arguments stay a JSON string. The caller decodes it.
