Tool execution and context-window management.

Two more stock callbacks

A callback is an object that the chat calls at fixed points in a turn. A backend attaches these two callbacks by listing them in _dflt_cbs. The Chat base class lists none, and default_cbs=False turns the list off.

UsageCallback adds the token usage of a turn to chat.use. The usage is the sum over all model requests in the turn.

ToolReminderCallback appends tool_reminder_ to each message the user sends while the chat has tools. The text asks the model to summarize each tool result before it calls the next tool.

The loop

call_tool(tc) runs one tool call tc against the chat’s tools. If the tool raises an exception, the turn continues. The result is the exception as a string, for example ValueError: nope. The model reads this string and can try again.

A tool call that has the key server was already run by the provider. call_tool does not run it again. The result is (run by the provider).

token_count is the number of tokens in the conversation after the last turn. Chat.pct_full divides token_count by ctx_limit to give the fraction of the context window in use.

In one step, the loop checks every call for approval before it runs any of them. media_note writes the text that goes with pictures that tools return. The section on pictures below describes it.

ToolCallError

def ToolCallError(
    *args, **kwargs
):

A tool call was lost again after the model was asked once to send it again.

Every model reply passes through one repair step before the loop acts on it. The step uses coerce_tcs to convert the arguments of each call to the types that the schema of its tool declares.

A reply can contain a tool call that the loop cannot read, because its arguments were lost or are not valid. The loop never runs such a call. It does not end the turn either. It drops the tool calls of that reply and sends reparse_msg_ to the model. The message asks the model to send the call again as one clean <tool_call> block.

Reply Message sent to the model
A reply with a call that the loop cannot read reparse_msg_
A reply with a call that the loop cannot read, and truncated=True cut_msg_, which asks for the call in smaller pieces
A reply with the key reparse The text of reparse, which a backend sets. It replaces both messages above.
A call that is still unreadable after the retry unread_msg_, as the result of that call

The loop asks for the call again at most once in each _send or _stream call. A turn that runs out of tool-call budget makes a second such call for final_prompt, and that call has its own retry. A backend that knows why a call was lost puts the reason in the key lost of the reply.

The loop checks the second reply as follows. If the second reply fails to parse and lost is not empty, the loop raises ToolCallError with the text of lost. If lost is empty or missing, the loop stops asking. A reply without tool calls ends the turn. A reply that still holds unreadable calls gets a tool-result message for each of them, with the text of unread_msg_, and the loop continues with the next request to the model.

_send(msg) is the loop for a turn that is not streamed. If a model request fails because the context window is full, _send calls recover_context and continues with the reply that recover_context returns.

A backend to test against

_ScriptChat is a test backend. Its replies come from a fixed list, one reply for each model request. The tests need no real model.

_mk(script, **kw) makes a chat that uses _ScriptChat and replies from the list script. Each item in script is the reply to one model request. The chat has two tools. add returns the sum of two numbers. boom always raises ValueError.

The cells below run these cases:

  • a turn without tools
  • a turn with one tool call
  • arguments that arrive as strings
  • a call that the loop could not parse
  • a tool that raises
  • a call that the provider ran
class _ScriptChat(ToolLoopMixin, Chat):
    "A backend whose replies are scripted, for testing the loop itself."
    _runtime, ctx_limit, token_count = 'script', 8192, 0

    def __init__(self, model=None, *, script=(), fail=None, **kw):
        self.script, self.fail, self.steps, self.step_kw = list(script), fail, 0, []
        o = ChatOpts.create(kw.pop('opts', None), **kw)
        self._setup(model, o)
        self._set_tools(self.tools)

    def _next(self, kw):
        self.step_kw.append(kw)
        if self.fail and self.steps == self.fail[0]: self.steps += 1; raise self.fail[1]
        r = self.script[min(self.steps, len(self.script) - 1)]
        self.steps += 1
        return Resp({'role': 'assistant', 'usage': {'total_tokens': 10}, **r})

    def _model_step(self, **kw): return self._next(kw)

    def _stream_step(self, **kw):
        self._step_res = r = self._next(kw)
        if (th := thought(r)): yield {'channels': {'thought': th}}
        if (t := resp_text(r)): yield {'content': [{'type': 'text', 'text': t}]}

register_runtime(Runtime('script', _ScriptChat, ('script-',)))

The budget

A turn has a budget of tool calls.

Parameter Default Meaning
max_steps 10 The number of tool calls that one turn can use

When the budget is used up, the loop refuses each further call. The result of a refused call is budget_msg_. The loop then stops running tools, and the chat sends final_prompt as one more message. The model answers with the results that it already has.

In the first example, max_steps=1. The first add runs, the second is refused, and the closing round produces the answer. The next example shows that the loop asks for approval of every call in a step before it runs any of them.

call_add = {'content': '', 'tool_calls': [_call('add', a=1, b=2)]}

c = _mk([call_add, call_add, {'content': 'Enough.'}], max_steps=1)
test_eq(resp_text(c('go')), 'Enough.')
test_eq(c._budget_exceeded, True)
test_eq([m['content'] for m in c.hist if m['role'] == 'tool'], ['3', budget_msg_])
test_eq(c.hist[-2]['content'], c.final_prompt)   # the closing round was actually sent
test_eq([m['role'] for m in c.hist].count('assistant'), 3)   # each reply is recorded once
# approval is asked for every call before any of them runs
seen = []
c = _mk([{'content': '', 'tool_calls': [_call('add', a=1, b=2), _call('add', a=3, b=4)]},
         {'content': 'done'}],
        approve=lambda tc: seen.append(tc.get('function', {}).get('arguments')) or len(seen) == 1)
c('go')
test_eq(len(seen), 2)
test_eq([m['content'] for m in c.hist if m['role'] == 'tool'], ['3', 'Denied by human operator'])

Why a call was refused

An approval function takes a tool call and returns a value. The value decides whether the call runs and what the result is if it does not.

Approval function returns Result
A true value The tool runs.
A false object that has a reply() method The text of reply(), so the model learns why the call was refused. The tool does not run.
A plain False or None Denied by human operator. The tool does not run.
Not called, because the budget is used up budget_msg_

The last example shows tool_max_len. A tool result that is longer than tool_max_len characters is cut to that length and ends with ...[truncated]. The loop measures the length of the string that the model will see. A large list and a long string of the same length count the same.

# a denial that can say why passes its reason on, and the tool never runs
class _Refusal:
    "What an approver returns when it said no and can say why."
    def __bool__(self): return False
    def reply(self): return 'Denied by human operator. Reason given: no answer after 300s'

called = []
def spy() -> str:
    "Record that it ran."
    called.append(1); return 'ran'

c = Chat('script-1', runtime='script', script=[{'content': '', 'tool_calls': [_call('spy')]}, {'content': 'ok'}],
         tools=[spy], approve=lambda tc: _Refusal())
c('go')
test_eq([m['content'] for m in c.hist if m['role'] == 'tool'],
        ['Denied by human operator. Reason given: no answer after 300s'])
test_eq(called, [])
# a plain falsy answer keeps the old wording
for no in (False, None):
    c = _mk([call_add, {'content': 'ok'}], approve=lambda tc: no)
    c('go')
    test_eq([m['content'] for m in c.hist if m['role'] == 'tool'], ['Denied by human operator'])
# the budget speaks before the approver, whatever the approver would have said
c = _mk([call_add, {'content': 'ok'}], max_steps=0, approve=lambda tc: _Refusal())
c('go')
test_eq([m['content'] for m in c.hist if m['role'] == 'tool'], [budget_msg_])
c = _mk([{'content': '', 'tool_calls': [_call('add', a=1, b=2)]}, {'content': 'ok'}],
        tool_max_len=1)
c('go')
test_eq(c.hist[2]['content'], '3')          # exactly at the limit, so untouched
c = _mk([{'content': '', 'tool_calls': [_call('add', a=100, b=200)]}, {'content': 'ok'}],
        tool_max_len=1)
c('go')
test_eq(c.hist[2]['content'], '3 ...[truncated]')   # an int result is measured as the model sees it
# turn options reach every model step of the turn
c = _mk([call_add, {'content': 'ok'}])
c('go', temp=0.3)
test_eq(c.step_kw, [{'temp': 0.3}, {'temp': 0.3}])

Running calls at the same time

By default the calls in one step run one after another. Two options change this:

Option Value Effect
parallel_tools True The approved calls of a step run at the same time, each in its own thread.
parallel_tools A list of tool names The calls run at the same time only when every approved call in the step is to a tool in the list. Otherwise they run one after another.
max_parallel_tools An integer The most threads that run at the same time.

A step with only one approved call always runs that call alone. You name the tools yourself, because only you know which tools are safe to run at the same time. The loop records the results in the order of the calls in both modes.

import time
def slow(n: int) -> int:
    "Sleep briefly, then return n."
    time.sleep(0.05); return n

two = {'content': '', 'tool_calls': [_call('slow', n=1), _call('slow', n=2)]}

c = Chat('script-1', runtime='script', script=[two, {'content': 'ok'}], tools=[slow])
t = time.time(); c('go'); serial = time.time() - t
test_eq([m['content'] for m in c.hist if m['role'] == 'tool'], ['1', '2'])
c = Chat('script-1', runtime='script', script=[two, {'content': 'ok'}], tools=[slow],
         parallel_tools=True)
t = time.time(); c('go'); par = time.time() - t
test_eq([m['content'] for m in c.hist if m['role'] == 'tool'], ['1', '2'])   # order preserved
assert par < serial
# a name list allows only those tools; anything else falls back to running them one at a time
c = Chat('script-1', runtime='script', script=[two, {'content': 'ok'}], tools=[slow],
         parallel_tools=['something_else'])
t = time.time(); c('go')
assert time.time() - t >= serial * 0.8

ToolMedia is a string subclass from urai.msgs. It holds the text of a tool result and a list of pictures in media. Each picture is a file path or bytes.

When a tool returns ToolMedia, the text goes in the tool message as usual. The loop sends the pictures in a separate message:

  1. The loop records the results of every call in the step.
  2. The loop adds one user message after the last result.
  3. The message starts with a note from media_note that names the tools. The pictures follow the note.

The pictures come after all results so that each tool message stays directly after its call. OpenAI-style histories require this order.

Limit Name Value
Pictures in one step max_media_ 8
Size of one picture max_media_bytes_ 20 MB

The note names each picture that the loop left out. A picture is left out when it is over a limit, missing, or not an image. If the chat has media_in=False, the model cannot see images. The loop then sends the note alone, and the note says that the pictures could not be sent.

Cancelling

chat.cancel() stops a turn that is running. The loop does not ask the model again after the call.

Each approved tool call that has not started gets cancel_msg_ as its result and does not run. This holds in sequential and in parallel mode. A call that is already running finishes.

In the example, a callback calls cancel() before the first tool call runs.

c = _mk([call_add, {'content': 'ok'}])
c.cbs = L(c.cbs)
class _CancelAfterFirst(ChatCallback):
    def before_tool_calls(self): self.chat.cancel()
c.add_cb(_CancelAfterFirst)
c('go')
test_eq(c.hist[2]['content'], cancel_msg_)    # approved, but not run
test_eq(c.steps, 1)                           # ...and the model was not asked again

With parallel_tools=True the same cancellation leaves every call of the step unrun:

c = Chat('script-1', runtime='script', script=[two, {'content': 'ok'}], tools=[slow], parallel_tools=True)
c.add_cb(_CancelAfterFirst)
c('go')
tools_out = [m['content'] for m in c.hist if m['role'] == 'tool']
test_eq(tools_out, [cancel_msg_, cancel_msg_])
tools_out

When the window fills mid-turn

Tool results can be long. A turn with several long results can fill the context window before the turn ends. A model request that fails because the window is full raises a context error. The loop then calls recover_context, which does four things:

  1. It cuts each older tool result that is longer than mx characters to mx characters, and ends the result with ...[truncated to recover context]. The newest keep_last tool results are not cut.
  2. It calls _recreate_conv to rebuild the backend’s state from the history.
  3. It stops further tool calls in this turn.
  4. It adds final_prompt to the history and asks the model once more for an answer.
Parameter Default Meaning
mx 500 The length, in characters, that a long result is cut to
keep_last 4 The number of newest tool results that stay whole

If the last request fails too, recover_context raises ContextWindowExceededError. The loop raises any other error without a recovery attempt.

source

ToolLoopMixin.recover_context

c = _mk([call_add, {'content': 'recovered'}], fail=(1, RuntimeError('n_ctx exceeded')))

c = _mk([{'content': 'x'}], fail=(0, RuntimeError('connection reset')))

Streaming

_stream is the tool loop for a streamed turn. It follows the same rules as _send for tools, the budget, approval and recovery.

Call What _stream yields
stream=True Each chunk as markdown
stream='raw' Each chunk as a dict

At the end of each step, _stream closes an open thinking block, unless the stream is raw. If a backend returns a tool call without a chunk for it, _stream yields one chunk for each such call. The caller sees every call.

If the turn is cancelled during a stream, the text received so far becomes the reply. If no text arrived, the reply is cancelled_reply_.

The final reply is the return value of the generator. SaveReturn and AsyncChat store it in .value.

# a lost call the backend explains raises the second time when streamed, too
test_fail(lambda: ''.join(_mk([{'content': '', 'tool_parse_failed': True, 'lost': 'cut off'}])('hi', stream=True)), contains='cut off')
c = _mk([{'content': 'streamed plainly'}])
test_eq(''.join(c('hi', stream=True)), 'streamed plainly')
c = _mk([{'content': 'Let me add.', 'tool_calls': [_call('add', a=1, b=2)]},
         {'content': 'It is 3.'}])
out = ''.join(c('go', stream=True))
test_eq(out, 'Let me add.It is 3.')
test_eq([m['content'] for m in c.hist if m['role'] == 'tool'], ['3'])
# in raw mode the caller gets the chunk dicts, including the announced call
c = _mk([{'content': 'thinking about it', 'tool_calls': [_call('add', a=1, b=2)]},
         {'content': 'done'}])

test_eq(kinds, ['text', 'tool_call', 'text'])

closed_ = []

    try:
        yield {'content': [{'type': 'text', 'text': 'one'}]}
        yield {'content': [{'type': 'text', 'text': 'two'}]}
    finally: closed_.append(True)

next(s); s.close()

Keeping the window from filling

recover_context acts after the window has filled. The tools in this section act before a turn starts. They remove old messages so that the window does not fill.

The loop cannot remove messages one at a time. An assistant message that calls tools must stay with the tool results that answer it. If they are separated, the provider rejects the history.

msg_groups(hist) splits a history into groups. A group is one message, or one assistant message with its tool calls and the tool results that follow it.

evict_middle(hist, keep_first, keep_last) removes whole groups from the middle of the history and returns (new_hist, dropped). It keeps the first keep_first groups, which usually state the task. It also keeps the last keep_last groups, which hold the current work. The defaults are 2 and 8.

SlidingWindowCallback calls evict_middle before each turn. It does the following:

  1. It reads chat.pct_full, the fraction of the window in use.
  2. If the fraction is at or above threshold, it removes the middle of the history and rebuilds the backend’s state.
  3. It adds the number of removed messages to chat.evicted.

If summarize=True, the callback also makes one oneshot call that summarizes the removed messages. It puts the summary in their place as a user message and an assistant message. If the summary call fails, the callback removes the messages without a summary.

The callback does nothing when the chat has no ctx_limit.

Parameter Default Meaning
threshold 0.9 The fraction of the window in use at which eviction starts
keep_first 2 Message groups kept at the start of the history
keep_last 8 Message groups kept at the end of the history
summarize False Whether one oneshot call replaces the removed messages with a summary
mx 4000 Characters of removed conversation sent to the summarizer
